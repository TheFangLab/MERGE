# merge-cli — User Guide

`merge-cli` predicts the pathogenicity of human genetic variants. It is the
command-line counterpart to [merge.fanglab.cn](https://merge.fanglab.cn), aimed
at users who want to script it, run it in bulk, or keep their data on their own
machines.

It runs in two modes:

- **Remote** (default) — variants are scored by the MERGE server. Nothing to
  install beyond the CLI, no GPU needed.
- **Local** — everything runs on your hardware. No rate limits, no data leaves
  your machine, but you deploy the models you want to use.

Both modes produce the same MERGE score, because both use the same four ensemble
models bundled with the package.


| Situation | Without a key |
|---|---|

the request, the server uses it for that one call and does not store it; local
mode passes it to the AlphaGenome service running on your machine.

## 1. Install

```bash
pip install merge-cli
merge --version
```

Requires Python ≥ 3.11. The ensemble models ship inside the package — there is
nothing else to download for remote mode.

### Optional extras

The base install covers remote mode on every platform. Two extras add the rest:

```bash
pip install "merge-cli[mcp]"      # ask for predictions in Claude — see §11
pip install "merge-cli[local]"    # local mode: pysam, for FASTA/tabix reads
pip install "merge-cli[all]"      # both
```

`local` is separate because pysam publishes no Windows wheels, and remote mode
never needs it. Without it, local FASTA, dbNSFP/GPN-MSA tabix lookups and the
precomputed cache fall back to their remote equivalents instead of failing.

Verify with a real variant — BRCA1 p.Pro871Leu (rs799917), which ClinVar's
expert panel classifies as Benign:

```bash
merge predict --chrom chr17 --pos 43092919 --ref G --alt A
```

```
                            MERGE Prediction Result
╭───────────────────────────┬──────────────────────────────────────────────────╮
│ Variant                   │ chr17:43092919  G → A                            │
│ Gene / Transcript         │ BRCA1;BRCA1;BRCA1;…  /  ENST00000497488;…        │
│ Variant Type              │ coding                                           │
│ Genome Build              │ hg38                                             │
├───────────────────────────┼──────────────────────────────────────────────────┤
│ MERGE Pathogenicity       │ 2.1%  Likely Benign                              │
│ MERGE + AlphaGenome avera…│ - (splicing and non-coding variants only)        │
│ Features                  │ 6/6 computed                                     │
├───────────────────────────┼──────────────────────────────────────────────────┤
│ AlphaMissense             │ 0.0416                                           │
│ ESM1b                     │ -2.4843                                          │
│ GPN-MSA                   │ 7.1700                                           │
│ ...                       │                                                  │
╰───────────────────────────┴──────────────────────────────────────────────────╯
```

Watch the **Features** line. `6/6 computed` means nothing was imputed; anything
less means a model did not report and the ensemble filled that feature with a
training median. See §2, "Missing features are imputed, not fatal".

**Two scores, two scales — and the second one only on two variant classes.**
`MERGE Pathogenicity` is the ensemble, whose feature panels contain no
AlphaGenome column; it is returned for every variant. `MERGE + AlphaGenome
average` is that score averaged 1:1 with the percentile of one AlphaGenome
column among the MERGE benchmark variants, and it is offered for **splicing and
non-coding variants only** — a coding variant shows the row as "splicing and
non-coding variants only". On coding and non-SNV the best AlphaGenome feature
scores AUROC 0.571 / 0.512 held out, close to chance. On the benchmark the
average reaches AUROC 0.9567 on splicing and 0.9781 on non-coding variants,
against 0.9269 and 0.9472 for MERGE alone.

The average carries its own per-task cut-points and its own label — do not read
its percentage against the ensemble's 0.8/0.6/0.4/0.2 bands. On a splicing or
non-coding variant where AlphaGenome produced no value, the row reads
`- (unavailable: ...)` rather than quietly repeating the ensemble score. Exact
panels, cut-points and held-out numbers: `merge_cli/data/models/MODEL_CARD.md`.

> **Get the REF allele right.** REF is the base in the reference genome at that
> position, not the one you are testing away from. Writing `--ref A --alt G`
> here describes a variant that does not exist in hg38, and every sequence model
> will refuse it while the ensemble still prints a confident-looking number from
> imputed values.

## 2. Core concepts

### Four variant types, four models

MERGE does not use one model for everything. The variant type is detected
automatically and the matching model is used:

| Type | When | Model | Algorithm |
|---|---|---|---|
| `coding` | exonic SNV | `MERGE_coding` | Logistic regression (L2), 6 features |
| `splice` | splice-site SNV | `MERGE_splicing` | CatBoost, 8 features |
| `noncoding` | everything else, SNV | `MERGE_noncoding` | Histogram gradient boosting, 12 features |
| `nonsnv` | indel / MNV / delins | `MERGE_nonsnv` | XGBoost, 12 features |

Non-SNVs are recognised by allele length before anything else; SNVs are then
classified by ANNOVAR gene annotation. Override the choice when you already know
the answer:

```bash
merge predict --chrom chr1 --pos 69428 --ref T --alt G --ensemble-type coding
```

### The score

A probability between 0 and 1 that the variant alters function, with a label:

| Score | Label |
|---|---|
| ≥ 0.8 | Pathogenic |
| ≥ 0.6 | Likely Pathogenic |
| ≥ 0.4 | Uncertain Significance |
| ≥ 0.2 | Likely Benign |
| < 0.2 | Benign |

The labels name score ranges and match the web server. These are research predictions. They are not a clinical diagnosis and are not a
substitute for ACMG/AMP interpretation.

### Missing features are imputed, not fatal

Each ensemble model expects a fixed panel of model scores. Anything you did not
run is filled in with the training-set median. So a prediction with two models
available still returns a score — but the fewer real features it has, the closer
it drifts to the population base rate. `missing_features` in the JSON output
tells you how many were imputed; check it before trusting a number.

## 3. The models

Thirteen models are scored, and **all of them run by default**. A model you skip
has its feature median-imputed wherever an ensemble panel uses it. AlphaGenome is
reported and used only for the MERGE + AlphaGenome average, never inside an
ensemble, and NT-v2 is reported but not in any of the four deployed panels.
Switch any off with `--no-<name>`:

| Model | Flag to skip | What it scores |
|---|---|---|
| AlphaMissense | `--no-alphamissense` | Missense pathogenicity (lookup) |
| ESM-1b | `--no-esm1b` | Protein LM (lookup) |
| GPN-MSA | `--no-gpn-msa` | Conservation-aware genomic LM (lookup) |
| AlphaGenome | `--no-alphagenome` | Regulatory / splicing effects |
| Enformer | `--no-enformer` | Regulatory track changes |
| HyenaDNA | `--no-hyenadna` | Long-context DNA LM |
| NT | `--no-nt` | Nucleotide Transformer |
| Evo2 | `--no-evo2` | Genomic foundation model |
| Carbon-3B | `--no-carbon` | Genomic LM, 24 kb context |
| GENERATOR | `--no-generator` | Eukaryotic genomic LM |
| GENERATOR-v2 | `--no-generator-v2` | Newer GENERATOR |
| NT-v2 | `--no-nt-v2` | Multi-species Nucleotide Transformer |

In local mode each model needs its own service running (see §5). When one is not
available its feature is imputed and the prediction says so:

```
│ Features    │ 4/6 computed  (2 imputed: enformer_max_abs, enformer_pos_sum) │
```

Treat that line as the confidence gauge: the fewer features actually computed,
the more the score drifts toward the training-set base rate. A score built on
half an imputed panel is not comparable to one built on a full panel.

### Evo2 variants

`--evo2-model` chooses the weights for the main Evo2 score (works in both modes):

```bash
merge predict --chrom chr1 --pos 69428 --ref T --alt G --evo2-model evo2_7b_base
```

In local mode all three variants are scored by default, because
`evo2_7b_score`, `evo2_7b_base_score` and `evo2_1b_base_score` are separate
features and the non-SNV / noncoding / splice panels each use more than one.
Only one Evo2 model fits on a GPU at a time, so they are scored sequentially —
a few extra seconds per variant. Narrow the set when speed matters more than
coverage:

```bash
merge local predict --chrom chr1 --pos 69428 --ref T --alt G \
    --evo2-models evo2_7b        # primary variant only
```

`evo2_1b_base` needs FP8, i.e. a GPU with compute capability ≥ 8.9 (RTX 4000/5000
Ada, L40S, H100). Elsewhere its feature is left missing and imputed — which is
also what the public server does.

In remote mode the server scores one Evo2 variant (the one chosen with
`--evo2-model`, `evo2_7b` by default) and may queue it rather than answer
inline. `merge predict` then waits for the queued job, up to `--evo2-timeout`
seconds (180 by default; 0 disables the wait and leaves the feature imputed),
and prints a note if it does not arrive. The other two Evo2 features are
imputed in remote mode.

## 4. Remote mode

The default. No configuration.

### Single variant

```bash
merge predict --chrom chr17 --pos 43092919 --ref A --alt G
merge predict --chrom 17 --pos 43092919 --ref A --alt G --genome hg19
merge predict --chrom chr1 --pos 69428 --ref T --alt G --format json
merge predict --chrom chr1 --pos 69428 --ref T --alt G --format tsv
```

`--format json` is the one to script against: it carries every sub-model score,
the imputed values, and `missing_features`.

### Batch VCF

```bash
merge batch variants.vcf --email you@example.com
merge status <job_id>
merge status <job_id> --watch     # poll every 30s
```

Results are emailed when the job finishes.

### Skipping SHAP

Every prediction can produce a SHAP contribution plot. It costs time; skip it:

```bash
merge predict --chrom chr1 --pos 69428 --ref T --alt G --no-shap
```

## 5. Local mode

Local mode runs the models on your machine. Each model gets its own conda
environment and HTTP service on its own port — nothing is shared, so you deploy
only what you need.

### Requirements

- conda (Miniconda/Anaconda)
- an NVIDIA GPU for the deep models (CPU works but is impractically slow)
- a reference genome FASTA — **strongly recommended**, see below
- disk: 2–35 GB per model

### Step 0: check your machine

```bash
merge doctor
```

Reports your GPUs, which services are up, and which model files are present.

### Step 1: configure

```bash
merge local setup
```

An interactive wizard for the data directory, ANNOVAR, and the reference FASTA.

**About the reference FASTA.** The local services cut the exact sequence windows
the models were scored with when the ensemble was trained. With a local FASTA
they do this themselves; without one they fall back to fetching sequence context
from the MERGE server, which needs network access — and non-SNVs cannot be
scored at all. Get one:

```bash
wget https://hgdownload.soe.ucsc.edu/goldenPath/hg38/bigZips/hg38.fa.gz
gunzip hg38.fa.gz
merge local predict ... --genome-ref /path/to/hg38.fa   # or set it in `merge local setup`
```

### Step 2: deploy the models you want

```bash
merge local env setup --model evo2          # Evo2 (7B, ~14 GB weights)
merge local env setup --model carbon        # Carbon-3B
merge local env setup --model nt_v2         # NT-v2
merge local env setup --model enformer      # Enformer
merge local env setup --model all           # everything (large!)
```

Available: `evo2`, `hyenadna`, `nt`, `nt_v2`, `generator`, `generator_v2`,
`carbon`, `enformer`, `alphagenome`.

### Step 3: start and check

```bash
merge local env start --model evo2
merge local env status
```

```
Local Inference Service Status
  ● evo2         online  12.4 ms  http://localhost:5003  conda env: deployed
  ○ carbon       offline  Service not running  conda env: not deployed
    → Run first: merge local env setup --model carbon
```

### Step 4: predict

```bash
merge local predict --chrom chr17 --pos 43092919 --ref A --alt G
merge local batch variants.vcf --output results.csv
```

Or make local the default so plain `merge predict` uses it:

```bash
merge config set-mode local
merge config show
```

### Stopping

```bash
merge local env stop --model evo2
merge local env stop --model all
```

### Sharing one environment between models

`merge local env setup --model <name>` creates a dedicated conda environment per
model, but that is a convenience, not a requirement: **any environment with the
right dependencies can serve any model.** Several of these models need the same
stack (torch + transformers 4.x + pyfaidx), so one environment can back all of
them — saving tens of GB of disk and a lot of download time.

To do that, start the service with the interpreter of the environment you want:

```bash
CUDA_VISIBLE_DEVICES=2 nohup ~/miniconda3/envs/NT/bin/python -u \
    ~/.merge-local-servers/generator_server.py > ~/.merge-generator.log 2>&1 &
```

`merge local env status` reports which environment is actually behind each port,
so a shared setup is visible rather than surprising:

```
● carbon       online  5.2 ms  http://localhost:5005  running (env: NT)
● generator    online  5.4 ms  http://localhost:5006  running (env: NT)
● nt_v2        online  5.2 ms  http://localhost:5008  running (env: NT)
```

Two things to keep in mind when sharing:

- The shared environment must satisfy every model it serves — in particular
  `transformers<5` (NT-v2 fails to load on 5.x) and `pyfaidx` for the local
  FASTA windows.
- Model scores depend on the library versions that produce them. If you later
  run `merge local env setup --model generator`, the CLI will prefer that new
  dedicated environment on the next `env start`; if its transformers version
  differs from the shared one, scores can shift. Keep the versions aligned, or
  stay with one approach.

### Ports

| Model | Env | Port | VRAM |
|---|---|---|---|
| AlphaGenome | `alphagenome` | 5000 | — (remote API) |
| HyenaDNA | `hyenadna` | 5001 | ~2 GB |
| NT | `nt` | 5002 | ~3 GB |
| Evo2 (all variants) | `evo2` | 5003 | ~20 GB |
| Enformer | `enformer` | 5004 | ~4 GB |
| Carbon | `carbon` | 5005 | ~20 GB |
| GENERATOR | `generator` | 5006 | ~6 GB |
| GENERATOR-v2 | `generator_v2` | 5007 | ~6 GB |
| NT-v2 | `nt_v2` | 5008 | ~3 GB |

Services can live on another machine — point the CLI at them:

```bash
merge enformer configure --url http://gpu-box:5004
```

## 6. Models needing extra setup

### AlphaGenome — your own API key

AlphaGenome runs on Google DeepMind's servers, not on your GPU. You need a key
from <https://deepmind.google.com/science/alphagenome>:

```bash
merge local env setup --model alphagenome
merge alphagenome configure --api-key YOUR_KEY
merge alphagenome status
merge local env start --model alphagenome
```

The key is stored in `~/.config/merge-cli/config.json`. `ALPHAGENOME_API_KEY` in
the environment overrides it, which is the better choice for shared machines and
CI. Without a key the service reports the problem in `/health` and its features
are imputed.

### AlphaGenome and reproducibility

The client version is pinned to `alphagenome==0.5.1`, matching what the MERGE
server runs, so local and remote mode return identical AlphaGenome features.
Installing a different version changes which scorers are requested and shifts
the `*_mean` features by roughly 5-10%.

One caveat worth knowing: **AlphaGenome features are not reproducible over
time.** The model runs on Google's servers and is updated there. Re-running the
exact training script today does not reproduce the values in the MERGE training
tables — for one test variant `raw_score_max` reads 0.18 today versus 0.80 when
the tables were built. Pinning the client cannot prevent this; only Google
pinning the served model would.

The practical consequence: the six AlphaGenome features
(`alphagenome_raw_score_{max,min,mean}`, `alphagenome_quantile_score_{max,min,mean}`)
sit on a somewhat different scale than the benchmark tables. Evo 2, Carbon and
Enformer can also vary slightly across hardware and runs; use the released
feature tables to reproduce the reported scores.

### Enformer — weights plus the transform

Enformer is a TensorFlow SavedModel and needs a normalisation transform pickle
alongside it. The MERGE features were computed with that transform, so scores
produced without it will not match the ensemble.

```bash
merge local env setup --model enformer
merge enformer configure \
    --model-path /path/to/enformer_model \
    --transform-path /path/to/enformer.transform.pkl
merge local env start --model enformer
```

The weights come from TF-Hub (<https://tfhub.dev/deepmind/enformer/1>); a local
SavedModel directory works too.

**Enformer predictions are not bit-reproducible.** Its TensorFlow GPU kernels are
non-deterministic, so the same variant scored twice differs by a few percent.
That is inherent to the model, not to this CLI, and it means Enformer-derived
features carry some run-to-run noise.

## 7. Precomputed cache

The local precomputed VCF cache is **disabled in this release**: the tables
served for it predate the bundled models, so every variant is scored with the
current models. `merge precomputed status` reports this, and
`merge precomputed download` downloads only with `--force`. Precomputed MERGE
scores for the coding and splice-region candidate SNVs, including hg19 versions,
are available in
[MERGE-precomputed-scores](https://github.com/TheFangLab/MERGE-precomputed-scores/releases/tag/v1.0).
These are CSV downloads; the legacy VCF cache command does not install them.

## 8. Scripting

`--format json` gives the full result:

```bash
merge predict --chrom chr1 --pos 69428 --ref T --alt G --format json --no-shap \
  | jq '{score: .ensemble.ensemble_results[].score,
         type: .ensemble.ensemble_results[].variant_type,
         missing: .ensemble.ensemble_results[].missing_features}'
```

A VCF loop:

```bash
while IFS=$'\t' read -r chrom pos _ ref alt _; do
  [[ $chrom == \#* ]] && continue
  merge predict --chrom "$chrom" --pos "$pos" --ref "$ref" --alt "$alt" \
      --format tsv --no-shap
done < variants.vcf
```

For anything sizeable, use batch mode instead — it is far faster than a loop:

```bash
merge local batch variants.vcf --output results.csv    # local
merge batch variants.vcf --email you@example.com       # remote
```

### Local batch throughput

Measured on one RTX 5880 Ada shared with other jobs, all 9 local services up,
all three Evo2 variants scored: **~33 s per variant** (20 variants in 11 min).
Variants are processed one at a time, so the cost scales linearly — budget
roughly 9 minutes per 100 variants, or narrow the model set:

```bash
# ~3x faster: one Evo2 variant instead of three
merge local batch variants.vcf --output results.csv --evo2-models evo2_7b

# faster still: drop the heaviest models (their features get imputed)
merge local batch variants.vcf --output results.csv --no-carbon --no-enformer
```

The output CSV has one row per variant with 30 columns: coordinates, variant
type, gene, the MERGE score and label, and every sub-model score.

## 9. Troubleshooting

**`Service not running`** — the model is deployed but not started:
`merge local env start --model <name>`. Check `merge local env status`.

**Everything is `-` and the score looks like a base rate** — no features were
computed, so the ensemble returned the imputed prior. Check
`prediction.errors` in the JSON output for why.

**`only SNVs are supported`** — an older service is running; restart it. Current
services handle indels via haplotype construction.

**`non-SNV scoring needs a local reference FASTA`** — set `--genome-ref` or
configure it in `merge local setup`. Non-SNVs cannot use the remote sequence
fallback.

**`Device compute capability 8.9 or higher required for FP8`** — Evo2 needs an
Ada/Hopper GPU. Older cards (A6000, A100, RTX 3090) cannot run it; leave Evo2
off there and its feature will be imputed.

**CUDA out of memory** — services hold their weights resident. Stop the ones you
are not using (`merge local env stop --model <name>`), or spread them across
GPUs with `CUDA_VISIBLE_DEVICES`.

**`Could not import module 'EsmForMaskedLM'`** — a transformers 5.x environment.
The CLI pins 4.x when it creates environments; if you built one yourself,
`pip install 'transformers<5'`.

**Slow first prediction** — the model is loading (Evo2 takes 1–2 minutes).
Subsequent calls reuse the resident model.

## 10. Reproducibility

The local services reproduce the exact quantities the ensemble was trained on.
These windows and formulas are fixed and deliberately not configurable:

| Model | Score | Window |
|---|---|---|
| Evo2 (all) | mean_PLL(REF) − mean_PLL(ALT) | 8192 bp |
| Carbon-3B | logP_sum(REF) − logP_sum(ALT) | 24576 bp |
| GENERATOR / -v2 | NLL(ALT) − NLL(REF) | 600 bp, max_length 128 |
| NT-v2 | ‖emb(ALT) − emb(REF)‖₂ | 600 bp, max_length 128 |
| NT | ‖emb(ALT) − emb(REF)‖₂ | 8192 bp (SNV) / 600 bp (non-SNV) |
| HyenaDNA | next-token log-ratio (SNV) / NLL delta (non-SNV) | 1000 bp upstream / 600 bp |
| Enformer | alt − ref per track, normalised, 7 summary statistics | 393216 bp |

A shorter window does not just cost accuracy — it puts the feature on a
different scale than the model expects, and the MERGE score comes out wrong with
nothing looking wrong. If a model does not fit on your GPU, leave it off and let
the ensemble impute it.

## 11. Asking in chat (MCP)

MERGE can register itself as an MCP server, so you can ask an assistant such as
Claude for a prediction in plain language instead of composing a command line.

```bash
pip install "merge-cli[mcp]"
merge mcp install
```

`merge mcp install` finds the `merge-mcp` executable belonging to *this* install
and writes it into your client's config — the step that most often goes wrong
when the config is edited by hand, because the path differs between venv, conda,
pipx and uv installs. It detects Claude Desktop, Claude Code and Codex
automatically; pass `--client` to choose, `--scope project` to register for one
directory only, and `--dry-run` to see what it would write first.

**On Windows the `merge` command usually is not on PATH.** A system-wide Python
install puts `merge.exe` and `merge-mcp.exe` in
`...\AppData\Local\Python\<version>\Scripts\`, and pip prints a warning that the
directory is not on PATH — so `merge mcp install` answers *"'merge' is not
recognized as an internal or external command"* even though the install
succeeded. Run it through the interpreter instead:

```bat
python -m merge_cli mcp install
python -m merge_cli mcp status
```

This needs no PATH fix at all: the registration resolves `merge-mcp.exe` by
absolute path from the running interpreter, and MCP clients launch it by that
path. Adding `...\Scripts\` to PATH is optional, and if you do it, prefer the
Environment Variables dialog over `setx PATH` — `setx` truncates PATH at 1024
characters.

Any other MCP servers already in that file are left alone, the previous version
is saved to a timestamped `.bak`, and a config that does not parse is refused
rather than replaced.

**Restart your client**, then ask something like *"Is chr1:1040819 G>GC
pathogenic?"*.

```bash
merge mcp status       # where it is registered, and whether that still resolves
merge mcp uninstall --client claude-code
```

The MCP server always runs in remote mode: per-model scores come from
merge.fanglab.cn and only the final ensemble is computed on your machine, so it
never starts a local GPU service and needs no GPU. It exposes seven tools:

| Tool | For |
|---|---|
| `answer_variant_pathogenicity` | **Start here.** One variant string in, an interpreted answer out |
| `predict_variant` | Per-model raw scores, forced `ensemble_type`, SHAP, custom timeouts |
| `get_variant_type` | The class only (coding / splice / noncoding / nonsnv) |
| `submit_batch_vcf`, `check_batch_status` | A VCF, rather than a loop |
| `check_health`, `list_models` | Diagnosis, and what runs where |

`answer_variant_pathogenicity("chr1:1040819 G>GC")` parses the variant, picks
the panel, retries once in degraded form if a model stalls, and returns the
score together with the gene, the MANE Select transcript, the real ClinVar
record when one exists, and a `caveats` list saying when the score should not be
trusted. rsIDs and HGVS are refused with instructions rather than guessed at:
resolving them needs a transcript database this server does not have, and a
guessed coordinate would silently score the wrong locus.

### Making the agent find them (`merge skill install`)

```bash
merge skill install     # → ~/.claude/skills/merge-variant-pathogenicity/
merge skill status
```

Registering the server is not the same as the model using it. Clients that defer
MCP tool loading — Codex does, to keep the context small — may never show the
model that merge-cli is there, so "is this variant pathogenic?" gets answered
from memory while the tools sit one search away. Skill descriptions stay
visible; the bundled skill is what tells the model to go looking, and how to
read the result. It ships inside the package, so it versions with the tools it
describes; `merge skill install` copies it out and only ever touches its own
directory.

One command covers both agents. Codex does not read `~/.claude/skills/`, but it
does not need a plugin either — it searches `.agents/skills` in the working
directory, the repo root, and then `$HOME`, so `merge skill install` writes
`~/.agents/skills/merge-variant-pathogenicity/` for it. Pick one with
`--client claude|codex`, or use `--scope project` for one directory only.

This is the step that makes the difference in Codex. Registering the MCP server
is not enough: Codex defers tool loading, so the model can answer a variant
question from memory without ever noticing that merge_cli is available. The
skill is what puts it in front of the model.

### Distributing it as a Codex plugin (optional)

For sharing rather than installing locally, `merge plugin build` packages the
same skill with the MCP configuration and a manifest:

```bash
merge plugin build --out ./plugins     # → plugins/merge-cli/
```

```
plugins/merge-cli/
  .codex-plugin/plugin.json   manifest
  .mcp.json                   registers the server as merge_cli (7 tools)
  skills/merge-variant-pathogenicity/
  README.md
.agents/plugins/marketplace.json   how Codex discovers the above
```

Codex finds a local plugin through a marketplace file, so the command writes
that too, next to `--out`. It **merges**: a marketplace can already list other
plugins and carry a display name you chose, and both survive. A marketplace that
does not parse is refused rather than replaced — overwriting it would discard
every plugin registered in it.

The entry uses `installation: AVAILABLE` rather than `INSTALLED_BY_DEFAULT`,
because the plugin is inert without the Python package behind it: installing it
for someone who has not run `pip install "merge-cli[mcp]"` would register a
server that cannot start. Override with `--installation` / `--authentication`,
or skip the file entirely with `--no-marketplace`.

A copy of both is checked into the repository, and `tests/test_codex_plugin.py`
fails if either drifts from what the command produces — the skill in the plugin
and the one in the package have to be the same text.

The plugin's MCP entry runs `python -m merge_cli.mcp_server` rather than the
`merge-mcp` console script. A manifest is shared and static, so it cannot carry
the per-machine absolute path `merge mcp install` resolves — and on a stock
Windows install that script is exactly what is missing from PATH. If the
`python` on your PATH is not the interpreter holding merge-cli, use
`merge mcp install` instead.

Three behaviours worth knowing when reading its answers:

- A variant whose REF does not match the genome build is **refused** rather than
  scored, since the ensemble would otherwise be classifying imputed values.
- `predict_variant` waits up to `evo2_timeout` seconds (default 45) for the
  server's queued Evo2 job. If it does not arrive, the reply carries a top-level
  `notes` field saying so — read it alongside `missing_features`.
- **The call is time-bounded.** `time_budget` (default 120s) caps the whole
  call; past it, `predict_variant` answers with the features it has and explains
  the gap in `notes` rather than blocking. This is deliberate: MCP clients
  enforce their own per-call timeout and *discard* a slower answer, so an
  unbounded call returns nothing at all instead of something partial. A variant
  the server has cached comes back in about 20 seconds. Raise `time_budget`
  when you would rather wait than have Evo2 median-imputed.

Codex applies its own limits on top, and its defaults are too tight — a scoring
call gets cut off at 300s. `merge mcp install` therefore writes
`startup_timeout_sec = 120` and `tool_timeout_sec = 600` into the Codex entry.
If you registered it by hand, add those two lines yourself.
